## 一句话结论

它目前不是一个内置数字人模型的“一键生成器”，而是一套面向 Codex Agent 的数字人视频生产工作流：定义任务状态、外部能力接口、授权与付费闸门、剪辑规范和验收标准，并用三个本地脚本完成任务初始化、素材预检和成片交付检查。

因此，仓库单独运行不能把一张人物图变成会说话的视频；只有接入 TTS、人物视频生成、口型同步或修复、带词级时间戳的 ASR、时间线合成器后，才可能产出完整数字人视频。

## 能实现什么效果

### 仓库自身已经实现

1. **标准化任务目录**：从主题或脚本、人物图、可选音色样本和辅助素材创建 `job.json`，并生成脚本、音频、生成素材、剪辑、字幕和 QA 等目录。
2. **素材与授权预检**：使用 `ffprobe` 检查人物图、音频和辅助素材能否解码，并阻止未确认肖像权、成年人物、远程上传和声音克隆授权的任务进入远程生成。
3. **人工审核闸门**：要求人工确认单一清晰人脸、图片无意外文字，以及可选音色样本为单一清晰说话人；代码不会自动完成人脸或成年状态识别。
4. **成片标准化交付**：对已有成片进行响度标准化，输出高质量 master 和较小 share 版本，做完整解码、黑帧检测、媒体探测、九宫格接触表和交付报告。

### 接入外部能力后，工作流设计目标

- 人物主讲的竖屏或横屏数字人短视频；
- 屏幕演示 + 画中画人物讲解；
- 人物、B-roll、图片和图表混合的解释型视频；
- 与最终旁白对齐的字幕、逐词高亮、关键词动效和章节节奏；
- 对嘴不准片段的局部口型修复；
- 1080×1920/30fps 等规格的 master、share、字幕和 QA 记录。

人物是否稳定、口型是否准确、眨眼和手势是否自然，主要取决于外部数字人/图生视频与口型模型，不是本仓库代码本身保证的效果。

## 它如何做“数字人”

核心不是在本地训练或推理一个数字人模型，而是让 Agent 按下面的流水线选择并调用外部工具：

```text
主题/脚本 + 授权人物图
        ↓
脚本定稿 → TTS 旁白定稿（主时间轴）
        ↓
外部人物视频生成 / 短动作生成
        ↓
外部口型同步或局部修复 + ASR 词级时间戳
        ↓
时间线合成、字幕和关键词动效
        ↓
FFmpeg 响度、编码、黑帧和人工视觉验收
```

`job.json` 中只为 `voice_generation`、`main_presenter`、`short_motion`、`lipsync_repair`、`word_timestamp_asr`、`timeline_compositor`、`encoder_qa` 预留了能力槽位。上游没有给这些槽位实现 MiniMax、HeyGen、MuseTalk、Whisper 或其他供应商适配器。

## 当前缺失能力

| 能力 | 仓库内实现 | 影响 |
| --- | --- | --- |
| TTS | 否 | 不能生成旁白 |
| 图生人物视频/数字人 | 否 | 人物图不会自行说话或产生动作 |
| 口型同步/修复 | 否 | 不能保证音素与嘴型对应 |
| ASR 词级时间戳 | 否 | 不能自动得到逐词字幕时间 |
| 时间线合成/字幕渲染 | 否 | 没有真正的剪辑执行器 |
| 端到端示例或质量基准 | 否 | README 中的目标效果尚无样片证据 |
| 任务初始化、预检、交付 QA | 是 | 这部分可以独立使用 |

## 与 MiniMax 的关系

MiniMax TTS 可以填充 `voice_generation`，为最终旁白提供音频。官方 T2A v2 接口支持将 `subtitle_type` 设置为 `word`，可以直接取得词级时间戳；因此新生成旁白不必先经过 ASR，ASR 更适合作为旧音频的补全和交叉验收。但 TTS 不能自动填补本仓库的 `main_presenter` 和 `lipsync_repair` 槽位。

MiniMax H3 虽能接收图片、视频和音频参考，但官方文档明确要求使用按量付费 API；视频套餐也明确暂不支持 H3。控制台中 Token Plan 的“积分/Credits”与按量付费余额、视频套餐点数不是同一个概念，不能因为有 2,000 积分就推断 H3 已开通。

若没有 MiniMax Hailuo/H3 一类人物视频能力，最小可研究组合是：

1. 用 MiniMax TTS 生成旁白；
2. 用授权人物图作为身份输入；
3. 接入本地口型方案（例如 MuseTalk 类）或另一家 talking-avatar API；
4. 用 Whisper/WhisperX 类 ASR 获取字幕和词级对齐；
5. 实现一个 FFmpeg/Remotion 时间线合成器；
6. 复用本仓库的预检和交付 QA。

只接 TTS 而不补第 3 步，最多得到“静态人物图 + 旁白 + 字幕”，不是真正会说话的数字人。

## 第二阶段：已跑通的无付费原型

本研究子项目新增了三个可执行组件：

- [`src/capability_probe.py`](src/capability_probe.py)：只读探测命令、Python 包、缓存模型和密钥是否已配置，不请求网络、不输出密钥；
- [`src/minimax_tts.py`](src/minimax_tts.py)：默认只输出脱敏请求计划，只有同时提供 `--execute --confirm-billable` 才会请求 T2A v2，并优先保存 `word` 级字幕；
- [`src/asr_faster_whisper.py`](src/asr_faster_whisper.py)：使用本地 faster-whisper 输出词级 caption JSON 和 SRT；
- [`src/mock_presenter.py`](src/mock_presenter.py)：用音频能量驱动程序化人物嘴部开合，并将字幕和音频编码成 MP4。

已用工作区既有的 54.365 秒 MiniMax 中文旁白完成闭环：medium 模型输出 15 个字幕段和 172 个词时间，生成 H.264/AAC、540×960、24fps 的代理主持人视频。详细结果见[实验记录](experiments/minimax-existing-asr/README.md)和[无 H3 架构](ARCHITECTURE.md)。

这里的嘴部只是音量驱动的开合，不是音素级口型，也不使用真人脸。它证明数据链已打通，同时把剩余问题收敛为一个明确模块：接入 MuseTalk 类真实人脸口型模型或 talking-avatar API。

## 研究价值判断

- **工作流研究价值：较高**。状态机、主时钟、成本闸门、重试上限、授权记录和 QA 恢复规则比较完整，适合研究 Agent 如何可靠地编排昂贵且不稳定的媒体模型。
- **产品工程参考价值：中等**。初始化、素材探测和交付标准化可以复用，但真正的供应商适配、队列、缓存、时间线和可观测性需要补齐。
- **数字人算法研究价值：低**。仓库不包含人物驱动、音素到嘴型、身份保持或动作生成算法，也没有模型权重与训练代码。
- **当前成熟度：早期**。固定版本只有一次提交、没有发布版本、端到端测试、成片样例或质量基准，因此暂不标记为 `validated`。

## 已验证范围

本轮未调用任何付费模型或上传人物素材，完成了：

- `init_job.py --help` 与一次真实临时任务初始化；

## D-ID 只读连通性测试

D-ID 的 `/credits` 接口可以同时验证网络、API Key 和账户积分，并且不会创建视频或消耗积分。先复制 `.env.example` 为本地 `.env`，从 D-ID Studio 的账户设置生成 API Key，再执行：

```powershell
python src/did_probe.py --env-file .env --execute
```

`200` 表示网络和鉴权可用，并会返回积分信息；`401` 表示网络可达但 Key 缺失或无效。脚本不会输出 Key。实际创建 Talk 属于计费操作，留到只读探测通过并明确确认后执行。

## 第三阶段：D-ID 有意义基准样片

已使用完全合成的正面主持人头像和 11.4 秒 MiniMax 中文旁白，跑通 D-ID V2 Photo Avatar：本地上传图片与音频、创建 Talk、轮询、下载和积分对账。生成耗时 41.7 秒，消耗 1 积分，得到 1254×1254、25fps、H.264/AAC 的 11.424 秒视频。

新增 [`src/did_talk.py`](src/did_talk.py) 作为带显式计费闸门的适配器；完整输入、验收标准和结果见 [`experiments/did-meaningful-baseline/TEST_PLAN.md`](experiments/did-meaningful-baseline/TEST_PLAN.md)。试用账户输出带全画面重复 D-ID 水印，因此这条样片验证了技术链路，不代表无水印交付效果。

人工观看结论为产品质量不通过：口型自然度明显不足，且 V2 单图头像没有手势与可信的上半身表演。停止继续消耗 D-ID V2 积分；后续优先验证基于真人训练视频的 Digital Twin / Video Avatar，而不是继续优化单图 talking-head。

## 第四阶段：HeyGen Digital Twin + Remote MCP 实测

已通过 HeyGen 官方 Remote MCP 的 OAuth 连接账号，使用网页端训练完成的私人 Digital Twin `handapeng` 和同名中文克隆声音生成首个有效样片。生成使用 Video Agent、横屏单一 A-roll、无 B-roll、无字幕和无转场，以便只检查人物、声音、口型与动作。

实测结果：

- 成片 12.16 秒，1280×720、25fps、H.264/AAC；
- 从创建到完成约 4 分 05 秒；
- 人物稳定性、中文声音、口型和上半身动作明显优于 D-ID V2 单图头像；
- 眼睛在整段成片中几乎不眨，形成明显“假人感”；训练预览本身有眨眼，因此问题更可能出在本次动作采样/生成，而不是授权或输入视频完全缺少眨眼；
- 提示词已经要求自然眨眼，但没有可靠执行，说明眼睑与微表情不能只依赖自然语言提示保证，仍需成片人工 QA。

可公开播放的样片和完整结论已进入 [GitHub Pages 研究页](https://yydshly.github.io/0822_githubcode_study/demos/lanshu-create-ai-presenter-video/)。这条样片证明 HeyGen 可以填充 `main_presenter`，但不会自动补齐仓库中的任务持久化、成本账本、字幕合成、局部修复和交付 QA。

## 这个库真正的意义

这个库的价值不是替代 HeyGen、D-ID、MiniMax 或本地口型模型，而是把它们从“孤立按钮”变成可替换、可恢复、可验收的生产组件。更准确的产品定位是：

> 数字人视频的生产协议与控制层，而不是数字人生成引擎。

它固化了在模型调用之外、却决定能否长期生产的部分：

1. **输入和授权协议**：谁的人物、谁的声音、能否远程上传、是否允许克隆；
2. **主时间轴协议**：先锁定旁白，再让人物、字幕、B-roll 和动效围绕同一时间轴工作；
3. **供应商能力槽位**：将 HeyGen、MiniMax、本地 ASR、口型修复与合成器隔离，允许 A/B 和替换；
4. **费用与失败边界**：显式计费确认、重试上限、异步任务状态与恢复入口；
5. **交付证据**：成片规格、响度、黑帧、接触表、人工视觉验收和失败记录。

直接使用 HeyGen 更适合快速制作一条高质量视频；当目标变成持续生产几十或几百条内容、多语言版本、多尺寸渠道、多人审核或多供应商切换时，这种流程层才开始产生明显价值。

## 适用与不适用场景

| 场景 | 是否适合 | 原因 |
| --- | --- | --- |
| 批量知识口播、产品更新、课程和培训 | 适合 | 主持人、版式和交付规格稳定，脚本持续变化 |
| 同一内容的多语言、多渠道和多尺寸版本 | 适合 | 可统一管理声音、字幕、人物和时间线派生 |
| HeyGen、D-ID、本地模型的成本与质量 A/B | 适合 | 能力槽位和 QA 规则可以保持不变 |
| 有肖像、声音、远程上传和费用合规要求的团队 | 适合 | 授权与付费闸门是仓库最有价值的部分之一 |
| Agent 媒体工程、异步任务与失败恢复研究 | 适合 | 状态机、检查点、恢复和验收比单次调用更值得研究 |
| 只需要快速生成一条数字人视频 | 不适合 | 直接用 HeyGen 网页或 API 更快 |
| 数字人算法、训练、人物驱动或音素口型研究 | 不适合 | 仓库没有模型权重和训练代码 |
| 实时互动数字人 | 不适合 | 没有 WebRTC、流式驱动、知识库和会话运行时 |
| 零依赖、本地一键生成 | 不适合 | 关键模型、权重、CUDA 与合成能力都需外接 |

## 当前推荐落地组合

```text
脚本/选题
   ↓
MiniMax TTS 或 HeyGen Voice（旁白与词时间）
   ↓
HeyGen Digital Twin（人物、口型、上半身动作）
   ↓
原生词时间 / faster-whisper（字幕与交叉验收）
   ↓
FFmpeg / Remotion（字幕、B-roll、画中画和多尺寸）
   ↓
本仓库工作流（授权、费用、状态、恢复和交付 QA）
```

因此最佳结论不是“HeyGen 替代这个库”，而是“HeyGen 作为最成熟的 `main_presenter` 执行器，这个库负责把它纳入完整生产系统”。
