# Sub2API 产品研究简报

## 1. 产品定义

### 当前产品是什么

Sub2API 是一套自托管、多租户、面向 AI 账号池的 API Gateway。它把上游 OAuth、Setup Token、API Key、Bedrock 和 Service Account 等凭据建模为账号资源，通过分组和平台 Key 向下游应用提供访问。

它的完整价值链是：

```text
上游账号与 API
→ 账号池与模型能力
→ 调度后的稳定容量
→ 下游统一 API Key
→ 用量、配额、成本和审计
```

### 推荐的一句话定位

> 可信团队的 AI 账号与 API 容量控制平面。

### 推荐价值主张

在不向成员暴露上游凭据的情况下，让 Claude Code、Codex、Gemini CLI 和内部 AI 应用通过一个入口稳定访问团队拥有的 AI 容量，并获得可控制、可计量、可审计的使用体验。

## 2. 产品目标

### 一级目标

1. **统一访问**：降低不同 AI 产品、协议、账号和开发工具的接入成本。
2. **提高容量利用率**：把离散账号的并发和额度窗口调度成稳定容量。
3. **控制成本与权限**：明确谁、通过哪个 Key、使用了哪个模型和多少预算。
4. **降低凭据风险**：成员只接触平台 Key，上游 token 由控制平面托管和轮换。
5. **保持原生体验**：优先保证 Claude Code、Codex、Gemini CLI 的协议与流式行为正确。

### 二级目标

- 对上游限流、过载和局部故障自动降级；
- 在连续对话中维持合理 sticky，提高缓存利用率；
- 支持余额、订阅、项目预算等不同资源分配方式；
- 提供调度解释、成本报表和操作审计；
- 通过 Mock Upstream 合约测试持续追踪上游协议变化。

### 非目标

- 绕过平台风控或保证个人订阅账号不会被限制；
- 未经审查的公共账号拼车、转售或支付运营；
- 在每个 Provider 上实现所有多媒体能力；
- 用一个抽象抹平所有供应商差异；
- 仅以 Provider 数量或最低价格衡量产品价值。

## 3. 目标用户与任务

| 用户 | 核心任务 | 主要价值 |
| --- | --- | --- |
| 个人重度开发者 | 让多个编码工具复用自己的 AI 账号和 API | 一个入口、统一用量、减少配置切换 |
| 可信小团队管理员 | 给成员分配 AI 能力但不泄露上游凭据 | 权限、Key、并发、预算和账号池 |
| 企业研发平台团队 | 建设内部 AI Gateway 和成本中心 | 审计、策略、可靠性、项目归集 |
| AI 应用研发团队 | 在多个上游之间获得稳定调用 | 路由、故障切换、协议兼容 |
| 网关研究者 | 研究 SSE/WS、调度和计费状态机 | 完整而可读的工程样本 |

不建议把“匿名公众购买共享订阅额度”设为首要目标用户。这个场景虽然与现有支付和用户运营能力匹配，但上游条款、隐私、财务、欺诈和账号封禁风险远高于可信团队场景。

## 4. 核心能力

### 4.1 账号资源化

- 管理 OAuth、Setup Token、API Key、Bedrock 和 Service Account；
- 记录账号模型能力、并发、额度窗口、过期和健康状态；
- 支持代理、TLS profile、优先级、倍率和分组归属；
- 自动刷新部分 OAuth token，按错误进入 cooldown 或摘除。

### 4.2 API 产品化

- 向用户签发独立平台 Key；
- Key 支持分组、到期、IP ACL、总配额和滚动窗口；
- 支持余额与订阅两种主要访问权益；
- 隐藏上游账号和凭据。

### 4.3 协议与模型路由

- Anthropic Messages；
- OpenAI Responses/Chat Completions；
- Gemini native；
- Codex 专用路径；
- 图片、视频、语音、Realtime 和搜索等平台特定接口；
- Composite Group 根据模型别名选择平台并改写上游模型。

### 4.4 调度与可靠性

- sticky session 和 previous response 绑定；
- 账号并发槽与等待计划；
- 优先级、负载、排队、错误率和 TTFT 评分；
- 限流/过载 cooldown；
- 同账号重试与跨账号 failover；
- Redis 快照、DB fallback 和状态清理。

### 4.5 计费与运营

- 分类记录输入、输出、缓存、图片、视频、搜索和语音用量；
- 渠道价格、模型价格、长上下文与倍率；
- 余额、订阅、API Key 和账号配额；
- 支付订单、Webhook、退款、补单和多支付实例；
- 管理后台与用量/渠道监控。

## 5. 核心原理

```text
请求进入
  ↓
API Key 鉴权、IP/用户/分组/余额或订阅准入
  ↓
识别 endpoint、公开模型和目标平台
  ↓
生成 session hash，读取 previous-response/sticky
  ↓
过滤不可用账号并评分
  ↓
Redis 原子获取用户/账号并发槽，必要时等待
  ↓
注入上游认证并进行协议转换或透传
  ↓
处理 HTTP/SSE/WS、错误分类和安全的 failover
  ↓
解析 usage，计算价格和倍率
  ↓
PostgreSQL 幂等事务更新账单与配额
```

关键架构事实：PostgreSQL 负责长期业务事实，Redis 负责实时协调。任一侧异常都可能影响正确性；前者影响账号、权限和账务，后者影响并发、sticky、限流和任务状态。

## 6. 使用场景

### 场景 A：个人 AI 开发工作台

用户把自己的 Claude、OpenAI、Gemini 等账号统一接入，在 Claude Code、Codex 和脚本里只维护一个 Base URL。需要重点保护本地数据库和 token，不一定启用 SaaS/支付功能。

### 场景 B：可信团队内部网关

管理员托管上游账号，成员获得不同 Key、模型权限、并发和预算。最符合推荐产品定位，也是下一阶段最值得验证的场景。

### 场景 C：企业 AI 接入与 FinOps

把官方 API、Bedrock、Vertex 等合规渠道接入内部平台，按部门/项目归集成本。需要补充企业 IAM、KMS、审计、数据保留策略和高可用。

### 场景 D：AI 应用的多上游可靠性层

应用通过 Composite 和账号池获得 failover。但若目标主要是支持数百个官方 Provider，Provider-first 网关可能更合适；Sub2API 的优势在账号和原生工具深度。

### 场景 E：公开 API 分发

技术上已有用户、计费、支付和套餐能力，但属于高风险方向。只有完成许可证、上游条款、隐私、支付、税务、欺诈、退款和凭据安全评估后才能进入产品决策。

## 7. 可扩展方向

### 产品扩展

- 组织、项目、环境和成本中心；
- OIDC/SAML/SCIM 与细粒度 RBAC；
- 预算审批、异常消费和成本分摊；
- 使用策略模板和团队自助申请；
- SLA、状态页和供应商健康解释。

### 技术扩展

- 统一 Upstream Profile/Capability；
- 单一调度与准入核心；
- 结构化错误分类和熔断；
- Mock Provider 合约测试；
- KMS Envelope Encryption 与凭据轮换；
- 预授权/冻结/结算账务；
- OpenTelemetry、Prometheus 和调度解释；
- 多实例、跨地域和灾备。

### 生态扩展

- Azure OpenAI、更多 Bedrock/Vertex 能力；
- 标准 OpenAI/Anthropic-compatible Provider 插件；
- MCP/A2A Gateway；
- Webhook、审计导出和 SIEM；
- Terraform/Helm 和 GitOps 配置。

## 8. 产品演进阶段

| 阶段 | 产品目标 | 验收标志 |
| --- | --- | --- |
| Stage 1：可信团队基线 | 安全统一入口 | Mock 合约通过、凭据加密、安全默认值、单实例稳定 |
| Stage 2：可靠容量池 | 可预测调度 | 双实例不超卖、sticky/failover 可解释、Redis 故障策略明确 |
| Stage 3：成本控制平面 | 财务正确 | 预授权与结算、账单幂等、预算与对账无差异 |
| Stage 4：企业内部平台 | 组织治理 | 企业 IAM、RBAC、KMS、审计、SLO 和灾备 |
| Stage 5：受控生态 | 插件化扩展 | Provider Profile 稳定、插件合约和兼容矩阵自动化 |

公共商业运营不自动属于 Stage 5；它是一条需要独立合规立项的产品线。

## 9. 建议的北极星指标

主指标：**每周成功完成且账务可对账的受控 AI 会话数**。

护栏指标：

- P95 TTFT 与流式完成率；
- 上游 429 后恢复时间；
- sticky 非预期迁移率；
- Redis lease 泄漏和超卖次数；
- 账务重复/漏记/透支金额；
- 明文凭据和超期未轮换密钥数；
- 核心工具协议合约通过率；
- 每次版本升级的回归失败数。

这个指标组合把稳定性、财务正确性和安全放在请求量之前，更符合可信团队控制平面的长期目标。
