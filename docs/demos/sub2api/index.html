FINDINGS

第一阶段的三个核心判断

产品重心是账号池

它对订阅账号、额度窗口、账号并发、Prompt Cache 粘性和原生编码工具的投入，比对大量 Provider 的统一抽象更深。

Redis 属于正确性路径

并发槽、排队、sticky、限流、调度快照和异步任务都依赖 Redis；它失效时影响的不只是性能。

双调度器是复杂度中心

通用网关和 OpenAI 高级调度器并存，公开问题也反复指向 sticky、快照和恢复语义；统一准入核心应先于继续增加 Provider。

PRODUCT GOAL

建议目标：可信团队的 AI 容量控制平面

统一接入只是起点。真正的产品目标是把分散的账号、API、并发和额度窗口转化为稳定、可控制、可计量、可审计的团队 AI 容量，同时不向成员暴露上游凭据。

统一访问

Claude Code、Codex、Gemini CLI 和内部应用使用一个入口与团队 Key。

容量与成本治理

按账号健康、并发、额度窗口和成本调度，并按用户、项目和模型归集。

安全与审计

托管、加密和轮换上游凭据，让每次访问和计费都有可追溯证据。

PRODUCTION BOUNDARY

默认可运行，不等于默认可安全公网运营

上游 URL

URL allowlist 默认关闭，并默认允许私网地址和 HTTP。生产环境需要显式白名单、禁私网和出口网络控制。

敏感凭据

账号 token 以 JSONB 保存，支付配置当前为明文 JSON。数据库、备份和运维权限必须按密钥系统保护。

服务条款

上游 README 明确提示账号封禁和服务条款风险。技术可行不等于上游授权或商业合规。
